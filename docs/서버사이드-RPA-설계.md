# 서버 사이드 RPA — 폰·배포 사이트에서 서류 자동발급 (설계·실증·배포)

> 목표: 데스크탑 로컬 앱 없이도 **폰/배포 웹에서 "시작"만 누르면 서버의 브라우저가 정부24를 대신 조작**해
> 서류를 발급·신청. 본인인증(카카오/PASS 폰 승인)과 최종 제출만 사용자, 나머지는 자동.
> 2026-07 착수. 이 문서는 **되는 것·안 되는 것·남은 과제**를 과장 없이 적는다.

---

## 왜 "폰이 직접 정부24 조작"은 불가능한가 (허락 문제가 아님)

브라우저 안의 웹페이지(JS)는 **다른 출처(정부24)의 문서를 읽거나 조작할 권한이 없다**(Same-Origin Policy·
CORS). 이건 전 세계 모든 브라우저의 근본 보안 규칙이라 정부 부처가 허락해도 웹페이지 스스로는 못 한다.
은행 사이트가 다른 탭을 조종 못 하는 것과 같은 이유다. → **"직접"은 영원히 불가. 그러나 우회로가 있다.**

## 되는 길: 서버가 브라우저를 대신 돌린다

```
[사용자 폰/배포 웹]  ── "시작"(이름·생년월일·연락처, HTTPS) ──▶  [RPA 서버(클라우드)]
                                                                    │  Playwright 로 진짜 크롬 구동
                                                                    ▼
                                                              [정부24 / 복지로]
      [사용자 폰 카카오톡] ◀── 본인인증 푸시 ── (서버가 이름·생년월일 입력 시 발송)
      사용자가 '허용' 탭 ──────────────────────▶ 서버 브라우저 인증 통과 → 서류 발급
[폰]  ◀── 발급 PDF ── [RPA 서버]  (서버는 개인정보 저장 안 함: 메모리에서만, 발급 후 폐기)
```

**핵심: 본인인증은 서버 브라우저가 headless여도 된다.** 서버가 이름·생년월일·연락처를 입력하면 인증
푸시는 **사용자 폰의 카카오톡/PASS 앱**으로 가고, 사용자가 자기 폰에서 승인한다. 서버 화면을 볼 필요가 없다.

## 실증(2026-07-12) — 데이터센터 headless 브라우저의 정부24 접속

이 저장소 환경(데이터센터 IP)에서 `chromium.launch(headless=True)` 로 실측:

| 대상 | 결과 |
|---|---|
| 정부24 홈(`gov.kr/portal/main/nologin`) | **HTTP 200** · title '정부24' · 70KB |
| 주민등록등본 민원(`AA020InfoCappView.do?CappBizCD=13100000015`) | **HTTP 200** · title '주민등록표 등(초)본 발급 …' · 206KB 전체 로드 |

→ **안티봇이 서버(headless) 접속을 막지 않았다.** "폰→서버→정부24" 경로의 첫 관문(페이지 도달) 통과 확인.
   (로그인·간편인증·폼입력·제출 단계는 안티봇 표면이 더 넓어 실계정 리허설로 별도 검증 필요 — 아래 과제.)

## 정직하게, 남은 과제 (불가능이 아니라 '만들면 되는' 것)

1. **안티봇 심화 구간**: 로그인·간편인증·제출은 홈 로드보다 탐지가 깐깐할 수 있다. 완화: 실제 크롬 채널
   (`RPA_BROWSER_CHANNEL=chrome`)·정상 UA·`slow_mo`·필요 시 **거주지 IP 프록시**. 실계정 리허설로 확정.
2. **개인정보(PII)**: 이름·생년월일·연락처가 서버를 '경유'한다. 원칙: **메모리에서만 사용, 디스크·로그 저장
   금지, 발급 후 즉시 폐기**(`rpa/config.py` 개인정보 원칙 + `clear_docs_dir`/`RPA_DELETE_AFTER_DOWNLOAD`).
   토큰 게이팅(`token_ok`/`redact_status`)으로 상태·서류 열람은 시작자만.
3. **비용**: 클라우드에서 브라우저를 돌리므로 유휴 아닌 실행 시 CPU/메모리 사용. 파일럿 규모는 감당 가능.
4. **동시성**: 서버 브라우저 수 제한(`RPA_MAX_CONCURRENT`, 큐잉 이미 구현). 현장 다인 동시엔 대기.

## 프론트엔드 — '옵트인'으로만 켜지는 안전 설계

공개 배포 사이트에서 **아무나 PII를 임의 서버로 보내지 않도록**, 원격 RPA는 **명시적 옵트인**일 때만 켠다
(`src/lib/backend.ts`):

- `getConfiguredRemoteRpa()`: `localStorage.modoo_rpa_server`(**https** 서버 URL) **와**
  `modoo_rpa_consent==='1'`(명시 동의)이 **둘 다** 있어야 원격 RPA 베이스를 반환. 하나라도 없으면 로컬 전용.
- 우선순위: **로컬 에이전트 > 옵트인 원격 서버 > 동일출처(로컬 앱)**. 로컬이 있으면 PII가 기기 밖으로 안 나가게 로컬 우선.
- `caps.rpaRemote=true` 면 UI가 '내 정보가 서버를 거친다'는 동의 안내를 유지.
- 자동 감지된 클라우드(`VITE_API_BASE`)가 `rpa:true`를 보고해도 **옵트인이 아니면 절대 PII 미전송**(기존 보안 테스트 전건 유지).

`setRemoteRpaServer(url, consent)` 로 설정/해제(동의 화면에서 호출). https 아니면 저장 거부(평문 PII 방지).

## 백엔드 — RPA 서버로 배포하기

RPA 코드(`backend/rpa/*`, `api/routes.py`)는 이미 서버에서 동작 가능. 서버 모드 기동:

```bash
# 클라우드/VM (Playwright + chromium 설치된 호스트)
export RPA_ENABLED=1            # 명시 opt-in (fail-closed 기본이라 필수)
export RPA_HEADLESS=1           # 창 없이(서버라 화면 없음)
export RPA_BROWSER_CHANNEL=chrome   # 실제 크롬(안티봇 강함). 없으면 번들 chromium(--no-sandbox 자동)
export CORS_ORIGINS="https://biocode67.github.io"   # 폰/배포 출처만 허용
export RPA_DELETE_AFTER_DOWNLOAD=1  # 발급 PDF 회수 후 서버에서 삭제(PII)
uvicorn main:app --host 0.0.0.0 --port 8000
# playwright install chromium  (최초 1회)
```

- 프론트는 이 서버 URL을 '고급: 내 서버로 자동발급' 동의 화면에 입력 → `setRemoteRpaServer(url, true)`.
- 이후 폰에서 서류 발급/신청 시 이 서버로 요청 → 서버 크롬이 정부24 조작 → 폰 카톡 승인 → PDF 회수.

## 현장(복지관 7/13-14)과의 관계

- **현장 즉시 경로**는 여전히 **노트북 로컬 앱**(`run-local-app.bat`)이 가장 안전·안정(거주지 IP·실크롬,
  PII가 기기 밖으로 안 나감). 검증 완료.
- **서버 사이드 RPA**는 "폰만 있어도 된다"를 여는 **파일럿/로드맵 경로** — 위 실증으로 기술적 성립을 확인했고,
  실계정 리허설로 발급 완주를 검증하면 데모/시연 가능.
