## 슬라이드 3 — 아이디어 기획서 · 주제 제안 배경

**문제 — 신청주의 복지의 구조적 미수급**
- 대한민국 복지는 "신청해야 받는" 구조. 그러나 정보는 중앙부처·지자체·민간재단에 흩어져 있고(민간재단은 어떤 정부 포털에도 없음), 용어는 어렵고('기준 중위소득', '소득인정액'), 신청 절차는 복잡하다.
- 결과: **자격이 있어도 몰라서, 어려워서, 번거로워서 못 받는다.** 가장 필요한 사람(독거 어르신·중증장애인·위기청년·외국인)이 가장 접근하지 못한다.

**대상 사용자**
- 1차: 복지 정보 접근성이 낮은 취약계층 — 독거 어르신, 장애인, 한부모·다문화 가정, 위기 청년, 외국인 주민
- 2차: 부모·조부모의 복지를 대신 챙기는 가족, 사회복지 현장 종사자

**왜 AI Agent 기반 SW여야 하는가** (양식이 명시적으로 묻는 항목 — 정면 답변)
- 검색 포털(복지로 등)은 이미 존재한다. 문제는 검색이 아니라 **"찾고→이해하고→신청하고→관리하는" 전 과정의 부담**이며, 이 부담은 정보 제공만으로는 사라지지 않는다.
- 필요한 것은 사용자를 대신해 **인지(상황 파악)→판단(자격 선별)→행동(서류 발급·신청 실행)→관찰(마감·갱신 감시)** 의 루프를 자율적으로 도는 에이전트다. 챗봇이 아니라 이 루프 전체가 에이전트다.
- 단, 복지 대상자의 개인정보(소득·장애·가구)는 극도로 민감 → **개인정보를 서버로 보내지 않는 온디바이스 에이전트**라는 설계가 요구된다. 모두봄은 이 두 요구를 동시에 충족한다.

## 슬라이드 4 — 아이디어 기획서 · AI Agent 기능 및 구조 기획

**에이전트 루프 구조도** (도식 권장: 인지→판단→이해→행동→관찰 순환 다이어그램)

| 단계 | 기능 | 입력/데이터/실행 |
|---|---|---|
| 인지 | 1분 프로필 위저드 · **자연어 한 문장 분석**("72세 혼자 사는데 소득이 적어요") · 음성 입력 | 사용자 입력→규칙 NLU(환각 0 설계) |
| 판단 | 정부·지자체·민간 **5,200여 건**에서 자격판정(2026 공식 선정기준) — 확실한 것과 '관련 복지'를 신뢰도로 분리(과장 방지) | 실데이터 카탈로그(공공데이터 ETL)+클라이언트 복지엔진 |
| 이해 | 쉬운 말 결과·용어사전·**7개 언어 AI 답변**·TTS 읽어주기 | **온디바이스 신경망 임베딩**(multilingual-e5, 브라우저에서 직접 실행 — 서버 전송 0) |
| 행동 | 챗에 "다 담아줘"→저장, "서류 뭐 필요해"→필요서류 집계 · **정부24 서류 자동발급·복지 자동신청**(데스크탑 앱·브라우저 확장 RPA) | 하이브리드 챗(지식=LLM Gemini—Groq·Claude 자동 폴백/행동=로컬/폴백=규칙) + 화면을 읽고 다음 행동을 판단하는 실행 에이전트 |
| 관찰 | 신청 마감 D-day·갱신 임박·서류 미비 감시, 앱 열면 먼저 브리핑 | 온디바이스 모니터링 엔진 |

**안전장치(설계 철학)**: 본인인증·최종 제출은 법이 사람에게 요구하는 단계 — **human-in-the-loop로 의도적으로 남긴다.** 무인 대행은 설계상 배제.
