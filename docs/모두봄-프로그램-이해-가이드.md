## 1. 30초 요약 — 모두봄은 무엇인가

**"복지는 아는 사람만 받는다"** 를 없애려는 개인 복지 자산 관리 AI Agent입니다.
2026 AI·SW 중심대학 디지털 경진대회 SW부문 출품작.

사용자는 나이·소득·가구·장애·자녀 같은 **최소 정보만** 넣습니다. 그러면 프로그램이:

```
① 발견   약 5,300건 복지 카탈로그에서 "내가 받을 수 있는 것"만 골라낸다
② 이해   왜 되는지/안 되는지, 얼마인지, 뭐가 필요한지 설명한다
③ 실행   실제 정부24·복지로를 브라우저로 조작해 서류를 발급하고 신청서를 채운다
④ 관리   신청 이후 갱신·점검 시점을 챙긴다
```

핵심 차별점은 **③ 실행**입니다. 대부분의 복지 서비스는 "여기 링크가 있어요"에서 끝나지만,
모두봄은 Playwright로 **진짜 정부 사이트를 대신 조작**합니다.

> ⚠️ 단, **완전 무인 자동 제출은 하지 않습니다.** 본인인증과 최종 제출은 항상 사용자가 직접.
> 이건 기술 한계가 아니라 **의도된 설계**입니다 (→ §6 참조).

## 2. 가장 먼저 이해해야 할 것 — "실행 형태가 3가지"다

이 프로젝트를 처음 보는 사람이 가장 많이 혼란스러워하는 지점입니다.
**같은 프론트엔드 코드가 3가지 환경에서 서로 다른 기능 범위로 동작**합니다.

```
┌───────────────────────────────────────────────────────────────────┐
│  A. 웹 (정적 배포) — biocode67.github.io/modoo-bom/               │
│     설치 0분. 백엔드 없음.                                        │
│     ✅ 분석·탐색·AI 의미검색·챗봇·통화상담·계산기·사후관리         │
│     ❌ 자동 서류발급 / 자동 신청 (→ 공식 링크 안내로 폴백)         │
├───────────────────────────────────────────────────────────────────┤
│  B. 데스크탑 앱 (Windows 설치본) — backend/local_server.py        │
│     프론트를 localhost:8000 동일출처로 서빙 + Playwright RPA      │
│     ✅ A의 모든 기능 + 🚀 실제 서류발급·신청 자동화                │
│     ← RPA가 실제로 동작하는 곳은 여기다                            │
├───────────────────────────────────────────────────────────────────┤
│  C. 풀스택 백엔드 (선택) — backend/main.py                        │
│     FastAPI + LangGraph 10노드 + ChromaDB RAG                     │
│     ✅ 서버측 AI 분석 스트리밍·RAG 검색·LLM 챗봇                   │
└───────────────────────────────────────────────────────────────────┘
```

### 왜 이렇게 나눴나

* **프론트가 백엔드 없이도 완전 동작해야 한다** — 심사위원이 링크 하나로 즉시 체험할 수 있어야 하고,
  서버가 죽어도 서비스가 죽지 않아야 합니다. 그래서 자격판정 엔진·정책 카탈로그·AI 검색이
  **전부 클라이언트에 있습니다**.
* **RPA는 사용자 PC에서 돌아야 한다** — 정부 사이트 로그인은 사용자 본인의 인증이 필요합니다.
  서버가 대신할 수 없고, 해서도 안 됩니다.
* **무거운 AI 스택은 선택** — `local_server.py`는 chromadb·langchain을 **임포트하지 않습니다**.
  그래서 설치본이 수 초 만에 뜨고 PyInstaller 번들이 현실적인 크기가 됩니다.

### 코드에서 이 분기는 어디서 일어나나

`frontend/src/lib/backend.ts` → `checkBackend()`가 `/api/health`를 찔러보고,
`frontend/src/lib/useBackend.ts` 훅이 그 결과를 컴포넌트에 전달합니다.

```ts
// useBackend.ts — 이 훅의 caps 값이 자동화 UI 노출을 결정한다
const { ready, caps } = useBackend()
// caps.rpa === true 면 → AgentSubmitButton / DocumentCenter 노출
// 아니면            → 공식 사이트 링크 안내
```

**이 게이팅 패턴을 이해하면 프론트 코드의 절반이 풀립니다.** "왜 이 버튼이 웹에선 안 보이지?"의
답은 거의 항상 여기입니다.

## 3. 핵심 개념 5가지

### ① 정책 카탈로그 — 약 5,300건, 전부 실데이터

```
frontend/src/data/
├── policies.ts           POL-###  정부 복지 정책 124건 (정밀 규칙·검증 금액)
├── govPrograms.ts        SUP-###  지원사업 33건
├── privatePolicies.ts    PRV-###  민간재단 21건 (현대차 정몽구 스칼러십·아산SOS 등)
├── housingPolicies.ts    HOU-###  주택 공고 7건
├── financialPolicies.ts  FIN-###  정책서민금융 5건 (햇살론·미소금융 등)
└── catalog.ts            ↑ 5개를 합쳐 시드 190건 + 런타임 병합 관리
```

여기에 빌드 산출물 `frontend/public/policies.json`(공공데이터 OpenAPI로 수집한
중앙부처 460 + 지자체 4,683건)이 **런타임에 병합**되어 총 약 5,300건이 됩니다.
병합은 `App.tsx`의 `loadExternalCatalog()`가 유휴 시점(`requestIdleCallback`)에 수행합니다 —
첫 화면 페인트를 막지 않기 위해서입니다.

> 🚫 **가짜 정책은 단 한 건도 생성하지 않습니다.** ETL(`backend/etl/`)은 실데이터만 정규화합니다.

**시드와 공공데이터는 신뢰도가 다릅니다.** 시드(POL-)는 정밀 규칙 기반 자격판정이 가능하지만,
공공데이터(GOV-/LOC-)는 요약형이라 자연어 신호 추론밖에 못 합니다.
그래서 결과 화면이 **"핵심 복지" / "관련 복지"** 로 나뉘어 표시됩니다.

### ② 복지 엔진 — `welfare-engine.ts` (프론트의 심장)

`frontend/src/lib/welfare-engine.ts` (약 1,400줄). 백엔드 `mock_responses.py`를 포팅한 것으로,
**서버 없이 자격판정 전체를 수행**합니다.

가장 중요한 두 함수:

```ts
checkPolicy(policy, profile)   // 정책 1건 × 사용자 1명 → 자격 여부 + 신뢰도 + 이유
runAnalysis(profile)           // 전체 분석 파이프라인 (아래 참조)
```

`runAnalysis()`의 흐름 (`welfare-engine.ts:1346`):

```
extractKeywords(p)      프로필 → 요약문 + 검색 키워드
  ↓
getEligiblePolicies(p)  카탈로그 전수 × checkPolicy → 적격 목록
  ↓
generateGuides()        신청 가이드 생성
buildPortfolio()        예상 수령액 포트폴리오
buildNotifications()    생애이벤트 기반 알림
  ↓
AnalysisResult          결과 객체 (화면 전체가 이걸 소비)
```

**`checkPolicy`가 단일 진실원(single source of truth)입니다.** 자격 설명기
(`explainEligibility.ts`), 우선순위 추천(`priority.ts`), 챗봇 답변이 전부 이 함수를 재사용합니다.
자격 로직을 바꾸려면 여기 한 곳만 고치면 됩니다.

`checkPolicy` 안에 **정직성 가드**가 여럿 박혀 있는 게 특징입니다 — 예를 들어 대출 상품이나
심사·선발형 지원은 연령·소득이 맞아도 "강력추천"으로 단정하지 않고 저신뢰 '관련 복지'로
격하합니다. "신청하면 다 받는 현금급여"와 다르기 때문입니다.

### ③ 온디바이스 다국어 AI 의미검색 (헤드라인 기능)

`frontend/src/lib/semanticSearch.ts` — `transformers.js`로 **브라우저에서 직접**
신경망 임베딩 모델(`multilingual-e5-small`)을 돌립니다.

* 정책 벡터는 빌드 시 사전계산 (`npm run embed` → `public/policy-embeddings.json`)
* 런타임엔 **질의만** 임베딩 → 코사인 유사도
* 한국어·English·Tiếng Việt 교차검색 (외국인·다문화 사각지대 대응)
* **서버로 아무것도 전송하지 않습니다** — 프라이버시가 이 선택의 이유

관련 파일: `aiAnswer.ts`(검색결과 기반 요약, 환각 없음), `detectLang.ts`(언어 자동감지),
`onDeviceTranslate.ts`(브라우저 내장 Translator API로 결과 번역).

> 운영 참고: 첫 로드에 모델 ~128MB를 CDN에서 받습니다. 시연 전 프리워밍을 권장합니다.

### ④ RPA — 실제 정부 사이트 자동화

```
backend/rpa/
├── manager.py        RPATask 생명주기 + 지원 서류 15종 단일소스
├── base.py           브라우저 컨텍스트·스크린샷·프레임 순회 유틸
├── gov24_rpa.py      정부24 (등본·초본·소득금액증명 등 13종)
├── nhis_rpa.py       건강보험공단 (자격득실확인서)
├── work24_rpa.py     고용24 (피보험자격 이력내역서)
├── apply_rpa.py      복지로 신청 자동화
├── session.py        GovSession — 정부24 여러 건을 로그인 1회로 연쇄 발급
├── orchestrator.py   여정(journey) 엔진 — "전부 자동발급"
├── auth_autofill.py  간편인증 폼 자동입력 (4개 사이트 통일)
├── ai_fill.py        🤖 AI 폼 채움 — 접근성 트리 기반 3계층 (아래)
├── diagnostics.py    자가 관찰 — 실패 순간 화면 구조를 PII 없이 덤프
└── probe.py          실측 확인 — 새 서류가 자동발급 가능한지 사용자 PC에서 검증
```

**`ai_fill.py`의 3계층 구조**가 이 프로젝트에서 기술적으로 가장 흥미로운 부분입니다:

```
① 접근성 트리 인지    WAI-ARIA accessible-name 수집 (aria-label·label[for]·tr>th …)
                      ※ 값 내용은 수집하지 않음 (PII)
② 결정론 의미매칭     성명↔이름, 휴대폰↔핸드폰, 주민번호↔생년월일 동의어 매칭
                      → LLM 키가 없어도 라벨 변형에 견고
③ LLM ReAct 폴백      키가 있을 때, 남은 빈 칸만. 구조 보고 계획→실행→검증→재계획
                      → 로컬 실키/IME로 실행
```

**②가 키 없이도 동작한다**는 게 핵심입니다 — 데모 전제가 "키 없이도 전 기능"이기 때문입니다.

### ⑤ 정직성 원칙 — 이 프로젝트의 정체성

이건 "기능"이 아니라 **코드 전체를 관통하는 제약**입니다. 별도로 §6에서 다룹니다.

## 4. 사용자 여정별 코드 따라가기

실제로 코드를 읽을 때는 화면 흐름을 따라가는 게 가장 빠릅니다.

### 여정 A — "내가 받을 수 있는 복지 찾기"

```
① 진입    App.tsx  →  view === 'analyze'  →  sections/Analyze.tsx
② 입력    components/ProfileWizard.tsx    단계별 프로필 입력
          또는 components/QuickAsk.tsx    "35살인데 월세 살아요" 한 문장 → lib/parseQuery.ts
③ 판정    lib/welfare-engine.ts  runAnalysis(profile)
④ 저장    store/useAppStore.ts   setAnalysis(profile, result)   ← zustand persist
⑤ 표시    components/ResultsView.tsx  →  PolicyCard  →  PolicyDetailDrawer
```

**핵심 파일 3개만 읽는다면**: `ProfileWizard.tsx` → `welfare-engine.ts` → `ResultsView.tsx`

### 여정 B — "서류 자동 발급" (데스크탑 앱에서만)

```
프론트                                    백엔드(local_server)
──────                                    ───────────────────
components/DocumentCenter.tsx
  └ POST /api/documents/rpa-issue  ────▶  rpa/manager.py  start_rpa_task()
                                            └ rpa/gov24_rpa.py  실제 브라우저 기동
                                                ├ 정부24 접속 → 간편인증 화면
                                                ├ rpa/auth_autofill.py 이름·생년월일·전화 자동입력
                                                ├ 📱 사용자가 폰에서 직접 승인  ← 여기서 멈춤
                                                ├ 서류 폼 자동 선택·입력
                                                └ 발급 → saved_path
  └ GET /api/documents/rpa-status/{id} ◀──  진행상황 + 스크린샷 폴링
       (lib/liveTasks.ts 가 sessionStorage 45분 TTL 로 세션 연속성 보장)
```

여러 서류를 한 번에 받는 **"전부 자동발급"** 은 `rpa/orchestrator.py`의 journey 엔진이
`POST /api/journey/run`으로 처리하고, 정부24 서류가 2건 이상이면 `rpa/session.py`의
`GovSession`이 브라우저를 공유해 **로그인 인증 1회**로 연쇄 발급합니다.

### 여정 C — "복지 신청"

```
components/AgentSubmitButton.tsx
  └ 노출 조건: caps.rpa && lib/quickApply.ts isBokjiroApplyable(정책)
  └ POST /api/apply/start  ──▶  rpa/apply_rpa.py
                                  ├ 복지로 로그인 → 서비스 딥링크 이동
                                  ├ '신청하기' 클릭 → 착지 서비스명 대조 가드
                                  ├ 이름·생년월일·연락처 자동 입력
                                  └ ⏸ 최종 제출 직전 정지 ← 사용자가 직접 누른다
```

### 여정 D — 백엔드 AI 분석 (풀스택 모드, 선택)

`backend/main.py`를 띄웠을 때만 동작하는 경로입니다.

```
WebSocket /ws/analyze  →  agents/graph.py  LangGraph StateGraph 10노드
```

```
① profile_analyzer    프로필 분석 + 검색 키워드 추출
② policy_search       ChromaDB RAG 검색 (하이브리드: BM25 1.0 + 임베딩 0.6 RRF)
③ eligibility_check   LLM 자격 판별
④ reflection_check    ⇆ ③ 재판별 루프 (MAX_RETRIES=2)
⑤ guide_generator     신청 가이드 생성
⑥ doc_retrieval       서류 취득
⑦ portfolio_manager   복지 포트폴리오 요약
⑧ notification_agent  생애이벤트 알림
⑨ result_tracker      신청 결과 추적
⑩ orchestrator        최종 안내 메시지
```

* 상태는 `agents/state.py`의 `AgentState` (pydantic). `events` 필드가 `operator.add` 리듀서라
  **각 노드는 새 이벤트만 반환**하면 자동 누적됩니다.
* WebSocket은 `astream(stream_mode="values")`로 노드마다 누적 상태를 받아 새 이벤트만 흘려보냅니다.
* 노드를 추가하려면: `agents/nodes/`에 파일 → `graph.py` 등록·엣지 →
  `mock_responses.py`에 Mock 분기 → `AgentState`에 필드 추가.

## 5. 어디를 봐야 하나 — 디렉터리 지도

## 6. 절대 규칙 — 왜 이렇게까지 조심하나

복지는 **돈과 생계**가 걸린 영역이고, 주 사용자는 **어르신·정보취약계층**입니다.
"잘못된 안내"의 대가가 일반 앱과 다릅니다. 그래서 아래는 협상 불가 규칙입니다.

### 🚫 1. 날조 금지

가짜 데이터·가짜 상태·가짜 성공을 만들지 않습니다.
과거 `result_tracker`가 `random.choice`로 신청 상태를 지어내던 코드가 있었고, **삭제했습니다.**

### 🚫 2. 거짓 완료 신호 금지 — "미발급을 완료로 오보"가 최악의 결함

발급·신청이 **실제로 확인되지 않으면** `status`를 `done/completed`로 두지 않고
`error`(⚠️ 확인 필요)로 정직하게 표기합니다.

완료로 인정하는 **genuine 성공 신호**만 셉니다:
`success:True` · 새 창 열림 · 완료 텍스트 확인 · `saved_path` 파일 확인.

> 예: 건강보험 RPA의 `_wait_print`는 "버튼을 클릭했다"가 아니라 "새 창이 떴다 / 완료 텍스트가 있다"만
> 성공으로 셉니다. 버튼 클릭은 성공의 증거가 아닙니다.

이 규칙은 `backend/tests/test_rpa_honesty.py`가 **소스 계약 테스트**로 잠그고 있습니다.

### 🚫 3. 완전 무인 자동 제출은 설계상 불가 & 금지

정부 본인인증(카카오 등)은 사용자가 직접, **최종 제출도 사용자 확인** 후.
RPA는 폼 자동입력까지 하고 **제출 직전 정지**합니다.

기술적으로 못 해서가 아닙니다. 신청은 **비가역적이고 법적 행위**이기 때문입니다.
**human-in-the-loop가 정답**입니다.

### 🚫 4. PII 유출 금지

상태·진단 응답에 실명·파일경로·서류종을 유출하지 않습니다.
토큰 없는 폴러에게는 마스킹, 본인 토큰에만 원문. 진단 덤프(`diagnostics.py`)는 **값을 수집하지 않고**
화면 구조만 남깁니다.

### 🚫 5. 과장 금지

동작 범위를 부풀리지 않습니다. 미검증 기능은 **'베타·실험적'** 으로 정직하게 표시합니다.
`β` 배지가 UI 곳곳에 있는 이유입니다.

### 🚫 6. AI 서명 흔적 금지

커밋·코드·파일 어디에도 `Co-Authored-By: Claude` · "Generated with" 류를 넣지 않습니다.

## 7. 개발 환경의 특수 사정 — "자가 관찰·자가 치유"

이 프로젝트를 읽다 보면 `diagnostics.py`, `self_heal`, "팀원 확인 요망" 같은 표현을 자주 만납니다.
배경을 알아야 이해됩니다.

**개발 컨테이너에서는 실제 정부 사이트에 접속할 수 없습니다** (조직 프록시가 정부24·복지로를 차단).
즉 개발자가 실화면을 직접 볼 수 없습니다. 그래서 "스크린샷 → 추측 개발 → 실기기 오류" 루프에 빠졌고,
이를 끊기 위해 두 축을 도입했습니다.

```
① 자가 관찰 (diagnostics.py)
   실패한 순간, 그 화면의 접근성 트리·프레임·마커·URL을 PII 없이 파일 하나로 저장.
   사용자는 스크린샷 대신 [진단 복사] 한 번으로 실화면 구조를 전달할 수 있다.

② 자가 치유
   발급 폼이 '진행 신호 없음'으로 정체하면, 사람 개입 전에
   필수 select 재선택(결정론) + ai_fill LLM 재계획(빈 칸만)으로 스스로 보정·재시도.

③ 구조적 원인 추론
   예: 신형 plus.gov.kr은 간편인증 폼이 자식 프레임에 렌더된다 → 메인 page만 보던 코드가 불발.
   base._sibling_contexts 로 형제 프레임·창을 전수 순회하도록 통일해 해결.
```

**"(팀원 확인 요망)"** 표기가 붙은 커밋은 = *개발 환경에서 검증 불가, 실기기(팀원 PC) 확인 대기*
라는 뜻입니다. 억지로 "통과"시키지 않고 정직하게 남긴 것입니다.

## 9. 자주 하는 오해

**Q. "AI Agent"라면서 왜 LLM 호출이 이렇게 적나?**
A. 의도적입니다. 자격판정을 LLM에 맡기면 **환각으로 없는 복지를 안내**할 수 있습니다.
판정은 결정론적 규칙으로, LLM은 지식형 챗과 RPA 폼 채움 폴백에만 씁니다.
AI 의미검색은 LLM이 아니라 **온디바이스 임베딩**입니다.

**Q. 왜 프론트에 로직이 이렇게 많나? 백엔드로 옮겨야 하지 않나?**
A. §2 참조. "백엔드 없이도 전 기능 동작"이 설계 목표입니다. 정적 배포로 심사위원이
링크 하나로 즉시 체험할 수 있고, 프로필 데이터가 서버로 나가지 않습니다(프라이버시).

**Q. `mock_responses.py`와 `welfare-engine.ts`가 같은 일을 하는데 중복 아닌가?**
A. 의도된 포팅입니다. 백엔드는 풀스택 모드용, 프론트는 정적 배포용.
다만 **둘이 갈라지면 안 되므로** `backend/tests/test_engine_parity.py`가 파리티를 잠급니다.

**Q. 왜 자동 제출을 안 하나? 그게 진짜 자동화 아닌가?**
A. §6-3 참조. 비가역적 법적 행위 + 본인인증 필수. **못 하는 게 아니라 안 하는 것**입니다.

**Q. 테스트 개수가 문서마다 다른데?**
A. 활발히 늘고 있어서 문서의 스냅샷 숫자는 뒤처질 수 있습니다.
**정확한 수는 항상 `npm test` / `pytest`를 직접 돌려 확인하세요.**
