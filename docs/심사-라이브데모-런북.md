# 심사·참가자 라이브 데모 런북 — "설치 없이 자동 발급/신청", 안 터지게

> 목표: 심사위원·참가자가 우리 사이트에 들어와 **확장 설치 없이** 서류 자동발급·자동신청을 체험하되,
> 본인인증(폰)·최종제출만 본인이 하고 **동시접속에도 서버가 죽지 않게** 한다.
> 이 문서는 그 안전한 구성 방법과 **정직한 한계**를 정리한다.

---

## 0. 왜 그냥 클라우드 배포로는 안 되는가 (반드시 이해)

서버 RPA를 일반 클라우드(Render·EC2 등 **데이터센터 IP**)에 올리면 **정부24 안티매크로(Mbuster)** 가
데이터센터 IP·자동화 브라우저를 차단해 발급이 자주 실패한다. 그래서 배포 위치가 핵심이다.

**정답: 백엔드를 "발표자 노트북(가정용/행사장 회선 = 주민 IP)"에서 돌리고, 터널로 외부에 노출**한다.
프론트(정적, GitHub Pages)는 그대로 두고 백엔드 주소만 터널 URL로 가리킨다.

---

## 1. 구성도

```
[심사위원/참가자 브라우저]  ──HTTPS──▶  [정적 프론트(GitHub Pages)]
                                              │  VITE_API_BASE = 터널 URL
                                              ▼
                          [cloudflared/ngrok 터널]  ──▶  [발표자 노트북]
                                                            └ FastAPI + Playwright(RPA)
                                                               (주민 IP → Mbuster 회피)
```

- 각 사용자가 '자동 발급/신청'을 누르면 **발표자 노트북의 브라우저**가 정부24를 대신 조작한다.
- '인증 요청'까지 자동 → **카카오 인증 푸시는 그 사용자 본인 폰으로** 감(이름·생년월일·휴대폰으로 식별).
  사용자가 폰에서 [인증 허용]만 누르면 진행. **최종 제출도 본인 확인 후.**
- 진행 화면은 스크린샷 스트리밍(status 폴링)으로 사용자에게 보여준다.

---

## 2. 안전장치 (이번에 넣은 것 — "안 터지게")

`backend/rpa/manager.py`에 다중 사용자 안전 계층을 넣었다. 전부 환경변수로 조정:

| 환경변수 | 기본 | 역할 |
|---|---|---|
| `RPA_ENABLED` | (자동) | `1`로 명시하면 클라우드 감지와 무관하게 RPA 켬. 데모 노트북에서 `1` 권장 |
| `RPA_MAX_CONCURRENT` | `2` | 동시에 띄우는 브라우저 수. 노트북 사양에 맞춰 2~3 권장(초과 요청은 자동 대기) |
| `RPA_MAX_QUEUE` | `8` | 대기 큐 최대. 넘치면 **503 + 정중한 안내**로 거절(프론트는 공식 링크로 폴백) |
| `RPA_TASK_TIMEOUT` | `900` | 태스크 하드 타임아웃(초). 멈춘 세션이 슬롯을 영구 점유하지 못하게 |
| `RPA_MAX_TASKS` | `200` | 태스크 저장소 상한(오래된 것부터 제거 → 메모리 무한증가 방지) |
| `RPA_HEADLESS` | `0` | 다중 사용자면 `1`(창 없이) 권장 — 스크린샷 스트리밍으로 진행은 보임 |
| `RPA_SHARED` | (없음) | **공유/터널 배포 시 `1` 필수** — '내 서류함' 계열(목록·등록·삭제·폴더열기)을 403으로 꺼서 이용자끼리 서류 표시명(실명)·파일에 접근하지 못하게 함. 발급·신청 RPA는 그대로 |

- **용량 신호**: `/api/health`의 `capabilities.rpa_capacity`(active/waiting/accepting)를 프론트가 읽어
  이용자가 많으면 무설치 안내로 자연스럽게 유도.
- **자동 폴백**: RPA가 꺼졌거나(클라우드) 큐가 차면 프론트는 **정확한 정부24·복지로 딥링크(무설치 경로)** 로
  폴백한다 — 즉 최악의 경우에도 "설치 없이 정확한 발급 페이지로 이동 + 내 정보 복사"는 항상 된다.

## 3. 실행 순서 (행사장)

```bash
# ① 발표자 노트북: 백엔드 (행사장/가정 회선에서)
cd backend
python -m venv venv && source venv/bin/activate   # (Windows: venv\Scripts\activate)
pip install -r requirements.txt
playwright install chromium
# 키가 있으면 AI, 없으면 rule-based로 동작
RPA_ENABLED=1 RPA_MAX_CONCURRENT=2 RPA_MAX_QUEUE=8 RPA_HEADLESS=1 \
  uvicorn main:app --host 0.0.0.0 --port 8000

# ② 터널로 외부 노출 (둘 중 하나)
cloudflared tunnel --url http://localhost:8000      # 무료, 계정 없이
# 또는  ngrok http 8000

# ③ 프론트가 이 백엔드를 보게 (터널 URL로 재빌드/배포)
cd ../frontend
VITE_API_BASE="https://<터널주소>" npm run build && npm run deploy
```

**완성된 자동발급 흐름(실측 검증 2026-07-06)**: 사용자가 사이트에서 이름·생년월일·휴대폰 + **주민등록상 시도·시군구**
(신청 정보 폼)를 입력 → '자동' 클릭 → 서버 RPA가 정부24 로그인·간편인증까지 자동입력하고 **'인증 요청'까지 자동 클릭** →
📱 사용자는 카카오톡 [인증 허용]만 → 서버가 발급 폼에서 **회원정보 주소가 실제와 달라도 입력한 시도·시군구로 자동 정정** →
신청하기·발급까지 자동 → 카드의 **'발급 문서 받기 (PDF)'** 버튼으로 사용자가 자기 문서를 **바로 다운로드**.
Windows cp949 인코딩 크래시는 `main.py`에서 UTF-8 강제로 원천 차단(별도 env 불필요).

```bash
#   → 라이브(https://biocode67.github.io/modoo-bom/)가 이 백엔드를 감지해 '자동' 버튼 노출
```

리허설: 발표 전 `/api/health`에서 `capabilities.rpa=true`, `rpa_capacity.accepting=true` 확인.
정부24는 데모 직전 한 번 실제 발급을 끝까지(카카오 인증 포함) 예행해 세션·회선 상태를 검증.

## 4. 정직한 한계 (심사위원에게 그대로 설명해도 되는 선)

- **본인인증(카카오)·최종 제출은 본인이 직접** — 법적 필수이자 비가역이라 자동화하지 않는다(안전장치).
- **자동화되는 것**: 로그인 이동·메뉴 클릭·발급 폼/신청 양식 입력·'인증 요청'·서류 저장까지.
- **개인정보**: 이름·생년월일·휴대폰은 인증 자동입력에만 쓰고 **메모리에서만**(로깅·디스크 저장 안 함).
  그래도 처음 보는 데모에 실명 정보를 넣는 걸 꺼리는 심사위원에겐 **무설치 안내 경로**만 체험하게 해도 됨.
- **안정성**: 정부 사이트 DOM 변경·Mbuster·회선 상태에 영향받는다. 그래서 위 폴백(무설치 딥링크)이
  항상 살아 있고, 동시성 상한으로 서버는 죽지 않는다.
- **완전 무인(설치도 인증도 없이 자동 제출)은 설계상·법적으로 불가.** 그 방향의 정답은 공공 마이데이터
  API(이용기관 등록 필요)로, 별도 로드맵으로 둔다. → `docs/무설치-자동화-전략.md`

## 5. 권장 데모 시나리오 (안 터지고 임팩트 크게)

1. **모두가 동시에**: 추천·분석·금액계산·서류안내·신청 딥링크 체험 → 100% 클라이언트 동작, 서버 무관, 안 터짐.
2. **자동화 시연(1~2명)**: 발표자 또는 지원자가 자기 정보로 등본 자동발급을 라이브로 — 인증 요청까지 자동,
   폰에서 [인증 허용] → 발급 완료. 스크린샷 스트림으로 전 과정 노출.
3. 동시 트래픽이 몰리면 대기/폴백이 **오류 없이** 안내되는 것도 그대로 보여주면 견고함이 어필된다.
